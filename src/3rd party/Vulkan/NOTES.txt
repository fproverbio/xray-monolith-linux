Why volk instead of linking -lvulkan directly
----------------------------------------------
This machine has no Vulkan dev headers under /usr/include, no
pkg-config binary, and no unversioned libvulkan.so symlink (only the
versioned libvulkan.so.1) - so a conventional find_package(Vulkan) or
-lvulkan link cannot work here even though the runtime loader and Mesa
drivers are installed and functional. volk sidesteps this entirely: it
dlopen()s the loader at runtime (via CMAKE_DL_LIBS/libdl) and resolves
every Vulkan function pointer dynamically, so no link-time dependency on
libvulkan.so is needed at all. This is the standard, well-established
solution to this exact problem and is what future Vulkan call sites in
this port should use.

volk usage requirements for future call sites
-----------------------------------------------
1. volkInitialize() must be called exactly once, before any other Vulkan
   or volk API call (including vkCreateInstance). It dlopen()s the
   Vulkan loader and resolves the global entry points
   (vkGetInstanceProcAddr, vkCreateInstance, ...).
2. After vkCreateInstance succeeds, call volkLoadInstance(instance) (or
   volkLoadInstanceOnly(instance) if no device will be loaded through
   this same volk state) so subsequent instance-level and
   physical-device calls are resolved through pointers specialized for
   that VkInstance.
3. After vkCreateDevice succeeds, call volkLoadDevice(device). For best
   performance with a single VkDevice, device-level calls (vkCmd*,
   vkQueueSubmit, vkQueuePresentKHR, ...) should go through pointers
   loaded directly for that device (volkLoadDevice does this) rather
   than the instance-level trampolines, since the latter carry extra
   dispatch overhead. If the engine ever needs to support multiple
   VkDevice objects concurrently, use volkLoadDeviceTable(&table,
   device) per device instead of the global volkLoadDevice, and dispatch
   through the appropriate table - the global volkLoadDevice approach
   only tracks one device's function pointers at a time.
